# Standard API – Endpoint Implementation Convention

This document defines a standardized API convention for managing resources through consistent CRUD endpoints, resource-level Actions, and collection-level Operations. It establishes uniform endpoint structures, HTTP methods, request and response contracts, and status codes to ensure predictable APIs and enable automatic frontend client generation.

## 1. Endpoint Structure

Each resource must expose the following operations:

| HTTP Method | Endpoint          | Description                 |
| ----------- | ----------------- | --------------------------- |
| GET         | `/resources`      | Retrieve all resources      |
| GET         | `/resources/{id}` | Retrieve a resource by ID   |
| POST        | `/resources`      | Create a new resource       |
| PUT         | `/resources/{id}` | Update an existing resource |
| DELETE      | `/resources/{id}` | Delete a resource           |

`{id}` represents the resource identifier.

## 2. Conventions

- Use plural, lowercase resource names (e.g. `/users`, `/products`).
- Pass resource identifiers as path parameters.
- `POST` accepts a creation model (`CreateRequest`).
- `PUT` accepts an update model (`UpdateRequest`).
- `GET /resources` returns a collection of resource models (`Model[]`).
- `GET /resources/{id}` returns a single resource model (`Model`).
- `DELETE` returns an empty response (`204 No Content`).
- All endpoints must follow consistent response and error-handling conventions.
- HTTP status codes must accurately reflect the operation result.

## 3. Data Contracts

Each resource must define three contracts:

- `ResourceModel` – model returned by the API.
- `CreateResourceRequest` – payload required to create a resource.
- `UpdateResourceRequest` – payload required to update a resource.

Request contracts must not be directly coupled to database entity models.

## 4. Example – Users API

| Operation            | Request             | Response         |
| -------------------- | ------------------- | ---------------- |
| GET `/users`         | —                   | `UserModel[]`    |
| GET `/users/{id}`    | —                   | `UserModel`      |
| POST `/users`        | `CreateUserRequest` | `UserModel`      |
| PUT `/users/{id}`    | `UpdateUserRequest` | `UserModel`      |
| DELETE `/users/{id}` | —                   | `204 No Content` |

## 5. Extensions

Resource-specific endpoints can be added independently of the standard CRUD operations.

There are two types of extensions: **Actions** and **Operations**.

### 5.1. Actions

Actions operate on a specific resource and require its identifier in the URL.

Endpoint structure:

`/{resources}/{id}/{action}`

Examples:

- `PUT /users/{id}/activate`
- `POST /users/{id}/deactivate`
- `POST /orders/{id}/cancel`

Supported HTTP methods:

- `GET`
- `POST`
- `PUT`
- `DELETE`

Actions can define their own request and response contracts.

The resource identifier is always required. The request body is optional only when the action does not require a request payload.

### 5.2. Operations

Operations act on the resource collection rather than on an individual resource.

Endpoint structure:

`/{resources}/{operation}`

Examples:

- `GET /users/export`
- `POST /users/import`
- `POST /users/search`
- `DELETE /users/cleanup`

Supported HTTP methods:

- `GET`
- `POST`
- `PUT`
- `DELETE`

Operations can define their own request and response contracts.

`GET` and `DELETE` operations do not accept request bodies. `POST` and `PUT` operations can accept request bodies.

Operations do not require a resource identifier.

### 5.3. Extension Rules

- Actions and Operations must not replace standard CRUD endpoints.
- Each extension must have an explicitly defined HTTP method.
- Each extension must define its request and response types.
- Extension endpoint names must be unique within their respective API and must not conflict with standard CRUD method names.
- Use Actions for resource-level operations.
- Use Operations for collection-level operations.

## 6. Goal

The API must be predictable and consistent across all resources.

A standardized structure allows frontend API clients to be generated automatically, eliminating the need for custom implementations of basic CRUD operations for each resource.

The same convention supports resource-level Actions and collection-level Operations while preserving consistent endpoint structures and type-safe request and response contracts.

## 7. Example API set

| HTTP Method | Endpoint                      | Description                                 |
| ----------- | ----------------------------- | ------------------------------------------- |
| GET         | `/users`                      | Retrieves all users.                        |
| GET         | `/users/{id}`                 | Retrieves a user by ID.                     |
| POST        | `/users`                      | Creates a new user.                         |
| PUT         | `/users/{id}`                 | Updates an existing user.                   |
| DELETE      | `/users/{id}`                 | Deletes a user.                             |
| PUT         | `/users/{id}/activate`        | Activates a user account.                   |
| PUT         | `/users/{id}/deactivate`      | Deactivates a user account.                 |
| POST        | `/users/{id}/change-password` | Changes the user's password.                |
| POST        | `/users/{id}/reset-password`  | Initiates a password reset.                 |
| POST        | `/users/search`               | Searches users based on specified criteria. |
| GET         | `/users/export`               | Exports the list of users.                  |
| POST        | `/users/import`               | Imports users from provided data.           |
| DELETE      | `/users/cleanup`              | Removes inactive user accounts.             |
