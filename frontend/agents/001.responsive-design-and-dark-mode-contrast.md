Build a modern, modular frontend application skeleton using Lit, TypeScript and Vite.

The goal is to create a clean, scalable application foundation that can be extended with business functionality later. Focus on architecture, reusable infrastructure, developer experience, maintainability and clear separation of responsibilities.

TECHNOLOGY STACK

Use the following technologies:

1. Lit and LitElement for UI components and Web Components.
2. TypeScript with strict type checking enabled.
3. Vite as the development server and build tool.
4. Web Awesome (@awesome.me/webawesome) as the primary UI component library.
5. @lit-labs/router as the official Lit ecosystem router.
6. TanStack Query with @tanstack/lit-query for API query management and caching.
7. @dmytromykhailiuk/typed-local-storage for typed localStorage access.
8. Vitest for unit testing.
9. Open WC testing utilities for Web Components testing.
10. ESLint for code quality and static analysis.
11. Prettier for consistent code formatting.

Use compatible package versions and verify the current APIs before implementation.

IMPORTANT ROUTER REQUIREMENTS

Use @lit-labs/router exclusively.

Do not install or use Vaadin Router, React Router or any other routing library.

The Lit Labs router is an experimental package. Check its current API and compatibility before implementation. Do not assume APIs from other router libraries.

Check browser support for URLPattern and install urlpattern-polyfill if necessary.

Use the official reactive controller API provided by @lit-labs/router.

- After successful login, redirect users to their originally requested protected route when possible, otherwise to /dashboard.

HTTP STATUS CODE HANDLING

Implement the following centralized behavior:

HTTP 401 Unauthorized:

- Clear the in-memory authentication state.
- Redirect the user to /login.
- Preserve the originally requested URL when practical.
- Prevent multiple concurrent 401 responses from triggering conflicting redirects.

HTTP 403 Forbidden:

- Redirect the user to /forbidden.
- Do not redirect to login.
- Do not automatically log out the user.

HTTP 404 Not Found:

- Unknown frontend routes must display the dedicated Not Found page.
- API 404 responses must remain normal API errors and be handled by the calling component.

All other API errors must be handled locally by the component or page that invokes the API.

Do not implement a complex global notification or error presentation system.

The shared HTTP client should only normalize errors and implement the centralized 401 and 403 behavior described above.

AUTHENTICATION

Implement basic in-memory authentication for prototype purposes only.

Do not implement production authentication.

Do not implement JWT, refresh tokens, OAuth, persistent sessions or cookie-based authentication.

Authentication state must exist only in application memory.

Create a centralized authentication store.

The store must expose:

- Current authenticated user.
- isAuthenticated.
- login(credentials).
- logout().
- Reactive state updates for subscribed Lit components.

Create the following User interface:

id: string
name: string
email: string

Implement a mock AuthApi with:

- login(credentials)
- logout()

Login should return a mock User object.

Logout should clear authentication state.

Authentication state must not be stored in localStorage.

After browser refresh, the user must be unauthenticated.

The implementation must be isolated so that real backend authentication can be introduced later without changing the rest of the application.

API LAYER

Create a centralized HTTP client based on the native Fetch API.

The HTTP client must:

- Use a configurable API base URL.
- Provide consistent JSON serialization and parsing.
- Provide typed responses.
- Support GET, POST, PUT, PATCH and DELETE.
- Support custom request headers.
- Support query parameters.
- Support AbortSignal.
- Provide a consistent typed API error structure.
- Handle HTTP status codes according to the HTTP STATUS CODE HANDLING section.

Do not expose raw URL strings throughout application components.

All API endpoints must be defined centrally as typed functions.

For example:

UsersApi.getAll()
UsersApi.getById(id)
UsersApi.create(request)
UsersApi.update(id, request)
UsersApi.delete(id)

Each endpoint must have explicitly defined request parameters and response types.

Components must import endpoint functions and call them directly.

Do not require components to manually construct URL paths or define response types.

Organize endpoint definitions by domain.

Keep API models and request/response types separate from UI components.

TANSTACK QUERY

Integrate TanStack Query using @tanstack/lit-query.

Create a centralized QueryClient.

Configure sensible defaults for:

- Query retries.
- Stale time.
- Cache garbage collection time.
- Refetch behavior.

Use queryKey and queryFn consistently.

Keep query definitions separate from components wherever practical.

Components should consume query controllers and automatically react to query state changes.

Use TanStack Query for:

- Server-state caching.
- Loading and error states.
- Refetching.
- Mutations.
- Query invalidation.
- Shared query data.

Use createQueryController outside render methods, preferably as a class field.

Use reactive options when query parameters depend on changing component properties.

Verify the current Lit adapter API and ensure compatibility with the installed TanStack Query version.
